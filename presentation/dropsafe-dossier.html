Orientation

Executive summary & contents

The 30-second pitch. DropSafe turns a hanging IV bag into a connected sensor. A load cell measures the bag's weight, an ESP32 converts it to millilitres, sounds a bedside alarm when the level is low, and publishes it over HTTPS to a serverless gateway. The gateway re-derives the volume and status from the raw weight, stores it in Firebase, and a React dashboard shows live volume, flow, time-to-empty and alert history from any browser — with no credentials in the browser and no network dependency for the local alarm.

The problem

IV bags are gravity-fed and are usually checked by eye at intervals. A 500 mL bag at 120 mL/h empties in about four hours, so the level between checks is unknown. Manual checks cost staff time, produce inconsistent documentation, and can delay replacement.

DropSafe adds continuous measurement and two independent warning paths: a local alarm at the bedside and a remote dashboard for a second observer.

The solution

Weight is measured continuously by a 5 kg load cell and HX711 ADC. The ESP32 converts gross weight to remaining volume, classifies the level, and drives a buzzer and LED without needing Wi-Fi.

Readings are queued and published over authenticated HTTPS. The gateway validates, recomputes and stores them; the dashboard subscribes read-only and renders trends, thresholds and alerts.

Design decisions that matter

Edge stays safe

Sampling and the buzzer/LED run in the main loop. Uploads run in a separate FreeRTOS task, so a slow or dead network cannot delay the local alarm.

Server is authoritative

The gateway never trusts the device's volume or status. It recomputes both from the raw weight, so a faulty or modified device cannot claim NORMAL.

Browser is read-only

Firebase rules allow public reads of monitoring data and deny all writes. Admin credentials and the raw device token never reach the frontend.

Framing

Problem, objectives & scope

1.1 Problem statement

An IV bag is a consumable with no instrumentation of its own. Staff infer the remaining volume from the drip chamber and the bag's printed scale, and record it when they happen to pass the bedside. Between observations the true level is unknown. The result is a monitoring gap: replacement can be late, documentation is sparse, and the same task competes with every other ward activity.

The project asks a narrower engineering question: can a low-cost, retrofittable load-cell rig measure a hanging bag continuously and deliver that measurement both locally and remotely, without making the local alarm depend on the network?

Functional

  • FR1 Sample weight at least once per second.
  • FR2 Convert gross weight to remaining volume and percent.
  • FR3 Classify NORMAL, LOW, CRITICAL or SENSOR_FAULT.
  • FR4 Drive a local buzzer and status LED.
  • FR5 Publish a reading every 5 seconds when connected.
  • FR6 Show live readings, trends and alert history in a browser.

  • FR8 Allow thresholds and demo interval to be configured.

  • NFR2 No service-account credentials or raw device token in browser code.
  • NFR3 All telemetry in transit over verified TLS.
  • NFR4 Short network outages must not lose the current state.
  • NFR5 Core logic must be unit-testable without hardware.
  • NFR6 Must run on a free-tier serverless host.
  • NFR7 Dashboard must be responsive and keyboard-accessible.

Key assumption: the bag hangs freely and vertically from the load cell. If the bag rests on a surface or the tubing pulls sideways, the measured weight — and therefore the volume — is wrong. The rig was calibrated specifically to avoid that condition.

What the examiner should hear: DropSafe is a monitoring instrument, not a treatment device. It estimates remaining volume from weight and provides warnings; it does not claim clinical accuracy and does not control the infusion.

Structure

System architecture

DropSafe is a six-tier system with two independent output paths. The sensing and edge tiers run on the rig; the gateway, storage and presentation tiers run in the cloud. The local alarm is deliberately outside the cloud path.

Figure 2.1 — End-to-end architecture. The device pushes to a serverless gateway; the browser only ever reads from Firebase.

2.1 Tier responsibilities

TierComponentResponsibility
Sensing5 kg load cell + HX711Convert mechanical load into a digital count; provide stable gross weight through a 24-bit ADC.
EdgeESP32 DevKitSample, tare/scale, compute volume/percent/status, drive buzzer/LED, queue and publish samples.
TransportHTTPS POSTSend JSON with a device token over verified TLS; retry with backoff; never block sampling.
GatewayVercel Node functionAuthenticate, rate-limit, validate, recompute volume/status, write atomically via Firebase Admin.
StorageFirebase RTDBHold the current bag snapshot, history, device heartbeat and published configuration.
PresentationReact dashboardRead-only subscription, local processing, charts, alert lifecycle, settings and exports.

2.2 Why a write gateway instead of device-to-database writes?

Trust and credentials

  • The Firebase service account stays server-side; it is never flashed to the device or shipped to the browser.
  • Only a SHA-256 digest of the device token exists in the gateway environment. The raw token exists only in the ESP32's git-ignored secrets.h.
  • The gateway recomputes volume and status from weight. A device that reports “NORMAL” with an empty bag is overruled.

Operational control

  • One place for schema checks, timestamp sanity, range limits and rate limiting.
  • One place to change thresholds or the fluid model without reflashing every device.
  • Serverless hosting gives a permanent HTTPS hostname and removes the old local server + tunnel dependency.
  • Trade-off: an extra network hop and occasional cold-start latency; acceptable at a 5 s publish interval.

3.2 Wiring and signal path

Figure 3.1 — Signal chain and pin assignment. The firmware uses GPIO 18/19 for HX711, GPIO 4 for the buzzer and GPIO 2 for the status LED.

3.3 How the measurement works

A load cell contains strain gauges bonded to a metal beam and wired as a Wheatstone bridge. Bending the beam changes the gauges' resistance, producing a small differential voltage proportional to load. The HX711 amplifies that signal and converts it with a 24-bit sigma-delta ADC; the ESP32 reads a signed count over a simple clock/data interface.

The firmware converts counts to grams with scale.get_units(3), which averages three conversions through the HX711 library's calibration factor. The factor is the bridge between raw counts and grams: grams = raw / CALIBRATION_FACTOR.

Why a load cell?

  • Weight is independent of bag shape, opacity and foil packaging.
  • It measures the actual mass consumed, so no optical line-of-sight is needed.
  • Low-cost, passive sensor with no fluids in contact with electronics.
  • Works with the bag hanging, which is how IV therapy is already delivered.

Mechanical rules for a valid reading

  • The bag must hang freely; bench contact removes load from the cell.
  • Keep tubing slack and avoid side pull on the hanger.
  • Tare with the cell unloaded; then attach the empty bag and subtract the fitted offset.
  • Keep the frame rigid; a flexible support introduces drift and noise.
Mechanical failure mode to mention: if the bag rests on the bench, the scale under-reports and the dashboard can show a false LOW or CRITICAL. This was a real debugging lesson; the final calibration and rig setup assume the bag hangs free.

Edge software

Firmware design

4.1 Execution model

The firmware uses two execution contexts so that networking can never delay sensing or the alarm. The Arduino loop() owns sampling and the buzzer; a FreeRTOS task pinned to core 0 owns queue draining and HTTPS. A mutex protects the shared ring buffer.

SETUPInitialiseSerial, GPIO, HX711, calibration factor, optional boot tare, Wi-Fi, first sample, queue mutex.
→
LOOP · 1 HzSense & alarmSerial commands, Wi-Fi check, NTP, read sample, classify, drive non-blocking buzzer/LED.
→
EVERY 5 sEnqueueCopy the current sample into the ring buffer; drop the oldest if full.
→
CORE 0 TASKPublishPeek, HTTPS POST, pop only if still the head; back off 5 s on failure.

4.2 Sample pipeline

#StepImplementation
1Check the ADCscale.is_ready(); if false, the sample is a sensor fault.
2Read and averagescale.get_units(3); reject non-finite, negative, or above MAX_LOAD_G (5000 g).
3Compute volume(weightG − EMPTY_BAG_TARE_G) / FLUID_DENSITY_G_PER_ML, clamped at 0.
4Compute percentvolumeMl / INITIAL_VOLUME_ML × 100, clamped to 0–100.
5ClassifyCRITICAL ≤ 25 mL, LOW ≤ 100 mL, otherwise NORMAL; invalid sample becomes SENSOR_FAULT.
6Populate metadataRSSI, uptime, device timestamp, sequence number, alarm flag.

4.4 The offline queue

The queue is a fixed-size ring buffer of Sample structs with head, count and a monotonically increasing seq. The producer is the 1 Hz loop; the consumer is the network task. Every access is wrapped in queueMutex.

  • Overflow policy: drop the oldest sample, never the newest. A short outage loses the beginning of the gap, not the current state.
  • Safe removal: the network task only removes the head if its seq still matches what it sent (popIfHead(seq)). If the producer overwrote it, the newer sample stays queued.
  • Why this matters: a dead gateway cannot stall the sampling loop, the buzzer, or the LED. The local alarm is independent of the queue.

4.5 Local alarm behaviour

StatusBuzzer patternToneLED
NORMALSilent—Off

The alarm is non-blocking: millis() % period < onMs decides the output state on every loop pass, so serial handling, Wi-Fi checks and sampling keep running. A state change resets the output before the new pattern begins.

4.6 Connectivity, time and TLS

Connection lifecycle

  • Station mode with auto-reconnect; explicit re-begin every 10 s if disconnected.
  • NTP (pool.ntp.org, time.google.com) runs after Wi-Fi is up; retries every 60 s.
  • Before time sync, the device sends timestamp 0; the gateway stamps the reading with server time.
  • Whole-second timestamps keep history keys stable across retries.

Transport security

  • WiFiClientSecure with the gateway root CA pinned via setCACert(ROOT_CA).
  • TLS_INSECURE 0 in production — certificate verification is never disabled.
  • Vercel's *.vercel.app chain was verified to GTS Root R1; that root is the pinned anchor.
  • Every request carries X-Device-Token; only its SHA-256 digest is stored server-side.

4.7 Serial calibration interface

status            → weight, volume, percent and current status
raw               → raw HX711 count and current calibrated units
tare              → zero the scale (load cell MUST be unloaded)
cal <known_grams> → with a known weight placed, print the new factor

The calibration factor is compiled into config.h. The serial command prints a candidate; it does not persist it, so a refit is a deliberate code change plus a reflash.

05
Measurement model

Processing, thresholds & calibration

5.1 The weight-to-volume model

remaining volume (mL) = (gross weight (g) − EMPTY_BAG_TARE_G) ÷ FLUID_DENSITY_G_PER_ML
remaining percent = clamp( volume ÷ INITIAL_VOLUME_ML × 100 , 0 , 100 )
flow (mL/h) = (earlier volume − later volume) ÷ (elapsed hours)
time to empty (h) = remaining volume ÷ flow

The model assumes 0.9% saline at 1.005 g/mL and a 500 mL nominal bag. EMPTY_BAG_TARE_G is a fitted zero offset, not the physical mass of the plastic bag. It is valid only together with the calibration factor; the two must be refitted as a pair.

5.2 Threshold classification

ConditionStatusMeaning in the UILocal output
volume > 100 mLNORMALAbove the low thresholdSilent
25 mL < volume ≤ 100 mLLOWApproaching exhaustionSlow beep
volume ≤ 25 mLCRITICALImmediate attentionFast high beep
weight invalid / sensor not readySENSOR_FAULTVolume and flow are unreliableLow periodic buzz

Thresholds are configurable in Settings and on the gateway. At a 500 mL nominal volume, 100 mL is 20% and 25 mL is 5%. These are classroom demonstration values, not clinical recommendations.

5.3 Flow estimation and time-to-empty

The dashboard estimates flow from the newest six valid points in the history. It walks backwards from the newest sample, skips faulty samples, and stops at a discontinuity marker (a manual level change, reset, or source switch) so an artificial jump is never interpreted as flow. It rejects a rising level, a negative rate, and anything above 2000 mL/h. Time-to-empty is then volume / flow; it is shown as unavailable when flow cannot be trusted.

Noise handling

Three ADC conversions are averaged per sample. The demo adds ±0.3 g of measurement noise and ±3% drip variation to exercise the pipeline.

Alert de-bouncing

An alert is created only when the status changes, not on every sample. This prevents a noisy threshold crossing from flooding the history.

Clamping

Volume never goes negative and percent never exceeds 100, so a slightly over-full bag or an empty bag still produces a sensible display.

5.4 Two-point calibration

The rig is calibrated from two stable, independently measured states: the emptied hanging assembly and the full bag. Both the factor and the tare are fitted together.

raw = gross grams × current factor
new factor = (raw_full − raw_empty) ÷ (known_full_mL × fluid density)
tare = raw_empty ÷ new factor

Calibration is a four-place invariant. The factor and tare are duplicated in the ESP32 config.h, the dashboard src/lib/calculations.ts, the gateway .env, and the documented constants. Changing one without the others produces a dashboard that disagrees with the stored history. .env.example is a template and may not contain the rig's fitted values.
Viva tip — the calibration story. An earlier attempt treated the tare as the physical bag mass (~30 g) and mis-scaled everything above 200 mL. The fix was to fit both the factor and the zero offset from the empty and full endpoints, then verify at mid-scale. If asked “what was the hardest bug?”, this is the answer: not the electronics, but separating the bag's mass, the hanging assembly's offset, and the ADC's scaling.

6.3 Device authentication

  • npm run device-token generates a random 32-byte token (64 hex characters), prints it once for secrets.h, and prints its SHA-256 digest for the gateway environment.
  • The gateway stores only DEVICE_TOKEN_SHA256. It hashes the presented header and compares with timingSafeEqual, so a wrong token does not leak information through timing.
  • Missing, empty or malformed tokens return 401 before any body parsing or database work.

6.6 Write semantics

  • One atomic update: history, current bag and device heartbeat are written in a single multi-path update(). A reader never sees a half-written sample.
  • Idempotent history: the history key is the device timestamp. If a reconnect retries the same sample, it overwrites the same key rather than duplicating it.
  • Monotonic current state: the current bag snapshot is only replaced when recordedAt is at least as new as the stored value. An old queued sample cannot roll the display backwards.
  • Retention: every 20 accepted writes, the oldest history is pruned to the configured 500 points. The counter is per serverless instance, so retained size can briefly exceed 500.
  • Offline heartbeat: online is set true on each write; the dashboard infers staleness from lastSeen rather than trusting a persistent flag.

6.7 Security rules

{
  "rules": {
    ".read": false,
    ".write": false,
    "monitoring": {
      ".read": true,

Browsers can read monitoring/… without a login, but cannot write anywhere. The gateway's Admin SDK bypasses these rules; no Admin credential is present in frontend code or VITE_* variables.

7.5 Alert semantics

  • Edge-triggered: an alert record is created only when a bag changes into LOW, CRITICAL or SENSOR_FAULT. Staying in the same state does not create duplicates.
  • Acknowledge ≠ resolve: acknowledging silences the browser tone and marks the record, but does not change the fluid status. A new status change creates a new unacknowledged alert.
  • Severity ordering: CRITICAL (3) > SENSOR_FAULT (2) > LOW (1). The most urgent unacknowledged alarm drives the sound.
  • Sound is opt-in: browsers require a user gesture, so sound starts off. Alarm patterns repeat every 5 s (LOW), 1.8 s (CRITICAL) and 3.5 s (SENSOR_FAULT).

Cloud link states

SIMULATED · USB · WAITING (connected, no device yet) · ONLINE · STALE · OFFLINE (socket down). Staleness uses max(30 s, 3 × publishInterval), so a 5 s publisher is marked stale after 30 s without a server timestamp.

Persistence and UX

Settings, alerts and added bag configs persist in localStorage with validation and try/catch. The UI uses hash routing, responsive sidebar, ARIA labels, reduced-motion support, toasts and an error boundary.

8.4 Demo workflow (simulator)

The demo bag starts at 420 mL and drains at 120 mL/h, but simulated time runs 120×: with the default 2 s interval, each tick advances four simulated minutes. A full bag therefore empties in roughly two minutes of real time, which is what makes a live classroom demo practical.

Inject a level

Simulate LOW sets the level halfway between the thresholds; Simulate CRITICAL sets it to 60% of the critical threshold.

Inject a fault

Simulate sensor fault emits a null weight, which becomes SENSOR_FAULT in the same pipeline as a disconnected HX711.

Recover

Restore normal clears the fault and lifts the level above LOW so the recovery path can be shown.

8.5 Alert lifecycle

  1. Normal → LOW: a status change creates one unacknowledged LOW alert; the dashboard and device both alarm.
  2. Acknowledge: the operator silences the alarm. The bag remains LOW; the record is marked acknowledged.
  3. LOW → CRITICAL: a new alert is created and acknowledgement resets; CRITICAL outranks LOW for sound.
  4. Refill / restore: a status change back to NORMAL closes the alarm condition. Historical alerts remain in the table.
  5. Sensor fault: any invalid weight produces SENSOR_FAULT; last valid volume is retained for context but flagged unreliable.

Security, reliability & limitations

9.1 Threat model and mitigations

9.2 Reliability features

Local-first alarm

Buzzer and LED are driven in the main loop, not by the cloud callback. Losing Wi-Fi does not silence the bedside alarm.

Bounded buffering

A 24-slot queue absorbs about two minutes of outage; overflow drops the oldest sample, preserving the current state.

Atomic persistence

History, current state and heartbeat commit together; timestamp-keyed history makes retries idempotent.

Stale detection

The dashboard infers ONLINE/STALE/OFFLINE from server timestamps instead of trusting a persisted flag.

Server-side validation

Range checks, timestamp windows and server-side reclassification reject malformed or stale payloads.

Automatic reconnect

The Firebase SDK reconnects; the ESP32 retries Wi-Fi every 10 s and drains the queue on recovery.

12.4 Likely viva questions

1. Why measure weight instead of using an optical or ultrasonic sensor?
Weight is independent of bag shape, opacity and foil packaging, and it directly measures the mass consumed. It also works with the bag hanging, which is how IV therapy is already delivered. The trade-off is mechanical: the bag must hang freely and the rig must be tared and calibrated.
2. How do you convert grams to millilitres?
Remaining volume = (gross weight − fitted tare) ÷ fluid density. For 0.9% saline, density is about 1.005 g/mL. The tare is a zero offset fitted with the calibration factor, not the physical mass of the bag.
3. Why the HX711?
A strain-gauge bridge produces a millivolt-level differential signal. The HX711 integrates a low-noise amplifier and a 24-bit ADC with a simple two-wire interface, so it can resolve the small changes from a hanging bag at low cost.
4. Why an ESP32 rather than a simpler microcontroller?
It combines Wi-Fi, dual cores, enough RAM for TLS and a queue, and FreeRTOS tasks. That lets sampling and the local alarm run independently of the network task. A smaller MCU would need a separate Wi-Fi module and more glue logic.
5. Why not let the ESP32 write directly to Firebase?
The service account would have to live on the device, and the device would be trusted to decide its own status. The gateway keeps Admin credentials server-side, stores only a token digest, rate-limits, validates and recomputes volume and status. It is a deliberate trust boundary.
6. What happens if Wi-Fi or the gateway goes down?
Sampling and the local buzzer/LED continue. Samples enter a 24-slot ring buffer, about two minutes at a 5 s publish interval. On reconnect the queue drains oldest-first at one sample per second; the history key is the timestamp, so retries do not duplicate.
7. How do you stop duplicate history entries?
The history key is the device's recordedAt timestamp. A retried sample overwrites the same key. The current snapshot only moves forward if the incoming timestamp is at least as new, so an old queued sample cannot roll the display back.
8. How is the device authenticated?
A 32-byte random token is flashed only into secrets.h. The gateway stores its SHA-256 digest and compares in constant time with timingSafeEqual. A missing or wrong token gets 401 before validation or database work.
9. Is the dashboard secure?
For this prototype, the key properties hold: the browser has no Admin credentials, no raw device token, and no write permission; TLS is verified with a pinned root. It is not a clinical security model — there is no staff login, audit trail or per-device key — and I can name those gaps.
10. How accurate is it?
The fitted rig reads about 492 mL for a 500 mL bag and ~248 mL at mid-scale — roughly 1.6% endpoint error and under 1% mid-scale. That is adequate for level awareness, not for billing or clinical volume measurement. A production device would need a tighter mechanical design and temperature compensation.
11. Why are the thresholds 100 mL and 25 mL?
They are 20% and 5% of a 500 mL bag — a practical classroom choice. They are configurable in Settings and on the gateway. They are not clinical recommendations and would be set by policy in a real deployment.
12. What was the hardest problem?
Calibration. An early version treated the tare as the physical bag mass, which mis-scaled everything above 200 mL. The fix was a two-point fit of factor and offset from the empty and full states, verified at mid-scale, and keeping all four copies of the constants aligned.
13. How do you test without the hardware?
The domain logic is pure functions and a pure reducer. The simulator feeds the same SensorReading shape as the real transports, so threshold, alert, flow and state tests run without a board. The suite is 139 tests across 11 files.
14. What would it take to deploy this in a hospital?
Per-device credentials and rotation, staff authentication and roles, an audit trail, alert escalation, a device registry, battery/enclosure design, clinical validation and a regulatory process. The current architecture is a prototype, not a certified medical device.
15. What is the next engineering step?
Multi-bag support with a device registry, per-device keys, battery and deep-sleep operation, OTA firmware updates, and a mechanical enclosure that guarantees free hanging and strain relief. On the software side, a shared rate-limit store and an audit log.
Closing line: “DropSafe is a small system with a clear trust boundary: cheap sensing at the edge, a safe local alarm, and a remote view that is useful precisely because the server — not the device or the browser — decides what is true.”

B.3 One-page formula sheet

Volume = (gross weight − tare) ÷ density
Percent = clamp(volume ÷ initial volume × 100, 0, 100)
Flow = (earlier volume − later volume) ÷ elapsed hours
Time to empty = volume ÷ flow
Calibration factor = (raw_full − raw_empty) ÷ (known_full_mL × density)
Tare = raw_empty ÷ calibration factor
Staleness window = max(30 s, 3 × publish interval)
Buffer duration = queue size × publish interval = 24 × 5 s ≈ 2 min
